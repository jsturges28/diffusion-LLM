    LLM Visualizer

    This tool visualizes how language models actually produce text, in real time. Its depth is in discrete diffusion: instead of generating one token at a time (left to right), a diffusion LLM starts from noise or masked tokens and iteratively refines an entire block over many denoising steps. A compact autoregressive (left-to-right) model runs alongside them as a baseline for contrast, and more model classes may join it. Use the Model selector in the header to switch between the available models (only one is resident in GPU memory at a time).

    How diffusion LLMs work

    The forward process corrupts text by independently replacing each token with a placeholder at a rate controlled by a noise schedule. The reverse process starts from a corrupted canvas and uses a Transformer with bidirectional attention to predict all positions simultaneously, then re-noises (re-masks) the least confident predictions. This repeats for N steps until the sequence converges. Unresolved positions are shown as ░ until they stabilize.

    Models

    LLaDA-8B-Instruct: the first competitive large-scale discrete diffusion language model, pre-trained on 2.3T tokens and instruction-tuned, comparable to LLaMA 3 8B. It performs masked diffusion over a single canvas with optional semi-autoregressive blocks, runs in bf16 (~17 GB VRAM), and supports interactive remasking / resume.

    DiffusionGemma-26B-A4B: Google's block-autoregressive text-diffusion model, a 26B-parameter Mixture-of-Experts (~4B active) built on Gemma 4, run here as a self-quantized 4-bit NF4 checkpoint (~18 GB VRAM). It denoises 256-token canvases with an entropy-bounded sampler and adaptive stopping (variable step count), chains canvases for longer outputs, and exposes an optional step-by-step reasoning (thinking) channel.

    SmolLM3-3B: a compact 3B-parameter autoregressive (left-to-right) decoder-only transformer, included as a baseline for contrast with the diffusion models. It streams tokens one at a time with per-token sampling confidence, runs in bf16 on GPU or CPU (selectable per activation, so GPU-less hosts can still use it), and exposes an optional reasoning (thinking) channel. Because it generates strictly left to right, it has no interactive remasking / Edit Frames; it carries its own explainability tools instead: per-token entropy, an optional top-5 Alternatives capture, and What If? substitution, which can force one of those five or any token you type, reporting what the model gave your choice and where it ranked.

    Help

    Quick start

    1. On the Main Menu, pick a model. Rows that will not fit in the available GPU memory are greyed out. Selecting one loads it and opens this generator (the generator is reachable only after a model is chosen).
    2. Wait for the model to load (the overlay dismisses automatically). To switch models later, use the Model selector in the header; it unloads the current model and loads the other, since only one fits in GPU memory at a time.
    3. Type a prompt in the text area.
    4. Adjust hyperparameters if desired, then click Generate.
    5. Watch the canvas resolve into text in real time; unresolved positions appear as ░.
    6. While the model runs, Generate is disabled and the status bar shows an animated Running… until the run completes.

    The status bar's left side carries the run's readouts: the current Step, the Elapsed wall-clock time, and T/s, tokens per second. Elapsed and T/s both count the run as a whole, so an edit continues from where the run had got to rather than restarting. T/s shows the run average by default; click it (or focus it and press Enter) to switch to the last step alone, which is noisier but shows throughput as it changes. The choice is remembered.

    The status bar's right side carries two things. Furthest right is the run's resting state, the line that stays put: Done., where a save landed, or the full text of an error. That one survives a trip to Analytics and back, and it is where every result is spelled out in full. Work that is happening appears to its left, as short messages that animate for as long as their operation runs and then leave, separated by a faint dot. They extend leftward, newest nearest the resting line, so two things at once both stay readable: entering What If? on an unsaved run saves the original in the background, and picking a candidate straight away leaves Saving original run and Running edit from frame 81 to end up together rather than one replacing the other. Because the resting line already spells out every result, a message simply disappears when its work succeeds instead of repeating what is sitting beside it.

    The row runs out to just short of the readouts on the left, and if there is ever more to say than fits, the oldest message fades out against that edge rather than being cut off. The resting line never gives up its own space to make room, since it is the one that has to still be there when you come back from Analytics.

    The motion is there to tell you which way work is flowing. A message rises in from the bottom of the window, and when its work is over it slips away to the left, out of the way of the resting line that takes over from it. Anything already up glides aside to make room rather than jumping, including when a long saved path arrives beside it. If your system asks for reduced motion, all of it becomes a plain fade.

    Messages name what they are acting on rather than just what they are doing. A save says whether it is writing the original or the edited run, since entering What If? or Edit Frames saves the pre-edit run on your behalf and it is worth knowing that is what you are watching, and it reports where the run landed as a path relative to the project folder either way. A resume names the stretch it is regenerating, Running edit from frame 12 to 40 when you resume to a chosen frame, or … to end when you resume all the way (which is always the case for a What If? substitution).

    The Main Menu model list is paginated: use the ‹ i/N › arrows to browse it. If a model's weights are not cached yet, its row shows Click to Download, which fetches them (with a progress bar, no GPU needed) before the model can be selected. You can navigate freely (menu pages, Analytics, Settings) while a download runs; a small draggable download toast tracks its progress from any page and returns you to the menu when you click it. An interrupted download resumes where it left off the next time you click.

    Header links move between pages: Menu returns to model selection, and Analytics opens the analytics suite. From Analytics, a Generation link appears whenever a model is loaded. A gear icon in the header opens the shared Settings page.

    Loading a model shows a progress bar with the phase underneath it. It opens on Starting worker, which is the model's process starting up and loading its libraries before a single weight has been read; there is nothing to measure yet, so the bar sweeps back and forth instead of showing a number. Once the weights start arriving it settles into a real reading: first Loading weights as they are read from disk, then Moving to GPU as they are copied across. That reading comes from watching how much memory the model has actually claimed against how much the checkpoint should need, so it tracks the real wait rather than counting files. For a checkpoint whose size cannot be worked out in advance, the phase is still named and the bar keeps sweeping rather than showing a number it would have to guess at.

    Switching models starts you on a clean slate: the previous run's output and metrics are cleared, because a new model is a new worker with nothing to say about the old run. This includes switching the same model between GPU and CPU. Your hyperparameters are kept, per model, until you close the app.

    Picking the model that is already loaded is not a switch. Whether you choose it from the Main Menu or the header, nothing is unloaded and no weights are read again, so its run is still there when you arrive. The menu says as much: selecting the resident model asks Go back to the Generation page? rather than offering to load it.

    Models

    LLaDA-8B-Instruct
    Masked diffusion over a single canvas with optional semi-autoregressive blocks. Supports interactive remasking / resume.
    DiffusionGemma-26B-A4B (NF4)
    Block-autoregressive diffusion over 256-token canvases with adaptive stopping and an optional reasoning channel. Because it denoises canvas-by-canvas with a variable step count, its status readout reads Step X, Canvas Y (the current step and which canvas it belongs to) rather than a fixed step total. Single-canvas runs support interactive remasking / resume (via seed-canvas re-entry); multi-canvas runs do not yet, so Edit Frames is disabled for them.
    SmolLM3-3B (autoregressive)
    A compact decoder-only transformer that generates left to right, streamed token-by-token with per-token sampling confidence. It runs on GPU or CPU (selectable per activation, so GPU-less hosts can still use it). Because generation is inherently left-to-right, it has no interactive remasking, so Edit Frames and Commit Order do not apply. It has its own explainability tools instead: per-token entropy (an Entropy overlay plus an entropy profile under the scrubber), an optional Alternatives capture shown on hover, and What If? substitution, which also makes Diff vs Original available. Its step counter is 1-based, so a full N-token run reads Step N/N.

    Hyperparameters

    LLaDA

    Steps
    How many denoising iterations run to turn a fully masked canvas into finished text. Each step unmasks a batch of the most confident tokens, so more steps let the model commit more gradually; this usually raises quality but is proportionally slower.
    Gen Length
    The size of the canvas: how many tokens the output can hold. The whole canvas exists from step 0 (as mask tokens) and is filled in place. Must be divisible by Block Length.
    Block Length
    Splits the canvas into left-to-right blocks that are diffused one after another (semi-autoregressive). Smaller blocks trade some parallelism for more left-to-right coherence; setting it equal to Gen Length gives pure, fully-parallel diffusion over the whole canvas.
    Temperature
    Controls randomness when sampling each token (via Gumbel noise). 0 is greedy/deterministic (always the argmax); higher values add diversity at the cost of stability.
    CFG Scale
    Classifier-free guidance strength. 0 disables it; higher values push the output to follow the prompt more closely by amplifying the gap between prompt-conditioned and unconditioned predictions.
    Seed
    Fixes the random number generator so a run is reproducible. Use −1 for a fresh, nondeterministic run each time.
    Remasking
    Which tokens get re-masked between steps. Low Confidence keeps the most confident predictions and re-masks the rest (the principled default); Random re-masks arbitrarily, mostly useful for experimentation.

    DiffusionGemma

    Max Tokens
    The output budget. DiffusionGemma generates in fixed 256-token canvases; when this exceeds 256 it chains multiple canvases block-autoregressively, committing one before starting the next.
    Denoising Steps
    The upper bound on denoising iterations per canvas. Thanks to adaptive stopping, a canvas often finishes early, once its predictions stop changing and the model is confident, so simpler prompts run faster than complex ones.
    Temp Start / Temp End
    Endpoints of a linear temperature schedule across the denoising steps. Starting hotter and cooling down lets the model explore broadly early, then sharpen toward a confident answer as the canvas converges.
    Seed
    Fixes the random number generator so a run is reproducible. Use −1 for a fresh, nondeterministic run each time.
    Thinking
    Enables a step-by-step reasoning pass before the answer. When on, the model's private reasoning is separated into a collapsible Reasoning panel above the output, keeping the final answer clean.
    Entropy signal
    Changes how per-token confidence is measured. Off (default), confidence is a fast stability proxy. On, it is the model's true certainty computed from the full output distribution (the max-softmax probability) at each step: more faithful, but slower and heavier, so enable it only when you specifically want to study confidence.

    SmolLM3 (autoregressive)

    Max Tokens
    How many tokens to generate. Because each saved frame is a full snapshot, the stream payload grows with the token count, so the recommended ceiling stays modest (and is lower on CPU, where decoding is slower).
    Temperature
    Controls randomness when sampling each token. 0 is greedy/deterministic (always the argmax); higher values add diversity at the cost of stability.
    Top-p
    Nucleus sampling: restrict each choice to the smallest set of most-likely tokens whose probabilities sum to p. Lower values keep only the very likeliest tokens (safer, less diverse); 1.0 disables the cutoff.
    Top-k
    A second, blunter cutoff: keep only the k likeliest tokens, whatever their probabilities. Where Top-p adapts (a confident model keeps few tokens, a torn one keeps many), Top-k keeps the same number either way, which caps how far into the tail sampling can reach when the model is uncertain. It is applied before Top-p, so the two compose as a hard truncation with a nucleus taken inside it. -1, the default, turns it off, which is a different thing from 0 candidates: a k of zero would leave the model nothing to sample and is not a setting you can ask for. Unrelated to the five candidates Alternatives records, which is a separate count.
    Seed
    Fixes the random number generator so a run is reproducible. Use −1 for a fresh, nondeterministic run each time.
    Thinking
    Enables an extended step-by-step reasoning pass before the answer. When on, the model's reasoning is separated into a collapsible Reasoning panel above the output, keeping the final answer clean.
    Alternatives
    Captures the five most likely tokens at every position, not just the one that was chosen. Hovering a token then shows what the model nearly said instead, and it is required for What If? substitution. On by default, since it is what the hover popover and What If? both run on; turn it off to save a little time per token.

    Confidence & the heatmap

    Every resolved token carries a confidence value in [0, 1], and each frame carries the mean confidence of its resolved tokens. What confidence means depends on the model:

    LLaDA
    The softmax probability of the token at the moment it was unmasked. It is recorded once and stays fixed for the rest of the run, since resolved tokens are never revisited.
    DiffusionGemma
    By default a lightweight stability proxy: how many consecutive steps a position has held the same prediction (so a freshly settled token starts low and climbs as it stays put). Enable Entropy signal to instead use the true max-softmax probability from the model's logits.
    SmolLM3
    The softmax probability of the chosen token at the moment it was generated. Like LLaDA, it is recorded once and stays fixed, since autoregressive tokens are never revisited.

    Hover any token in the output to read its confidence for the current frame in the metrics strip described below; masked / unresolved tokens report 0. Select Heatmap in the Overlay drawer (top-right of the output area) to recolor resolved tokens by confidence: dim, desaturated tones mark low-confidence tokens and bright green marks high-confidence ones. The heatmap is a live view over the frame you are viewing and is not saved. See Visual overlays & settings below for the other overlays.

    The metrics strip

    The thin row directly above the output is where a single token's numbers are read. Hover a token and it fills in: the token itself, its position in the canvas, its confidence and its entropy, each with a small bar on the same color ramp the overlays use. Whitespace tokens are shown with visible stand-ins (· for a space, ↵ for a newline), so a token that looks like nothing still reads as something.

    It is always there, holding its labels and showing a dash for each value while nothing is hovered, rather than appearing under the pointer and pushing the text down every time you cross into it. A dash means the run does not carry that value, which is not the same as zero: diffusion runs record no entropy at all, and a run saved before a signal existed was never measured rather than measured as nothing.

    Two things feed it. Hovering a token is one. Sweeping the entropy profile below the scrubber is the other, so a column that catches your eye can be read without moving the pointer to the text. The strip follows the frame as well as the pointer: hold still and scrub, and the numbers change under you as the position resolves. It works during live generation too, on tokens that have only just arrived. Under an overlay that knows something extra about a position, that is appended: Resolved at step N under Commit Order, or was: X under Diff vs Original. While both runs are stacked, the right-hand end names which one you are reading, Original or Edited. The Analytics detail modal carries the same strip above its own token view, fed by both its tokens and its entropy chart.

    The right half stays empty until you hover a row of the candidate popover, which fills it with that candidate's probability at full precision, headed by a green chip where the hovered token's own chip is grey. The two chips are the whole legend: grey is the token the run committed here, green is one it only weighed. The rows themselves round to a tenth of a percent, which is enough for the five the model actually considered and not nearly enough for a token you typed yourself, so the precision lives out here where there is room for it. Every row also reports its rank, as in #3 of 128,256 for the third candidate or #41,203 of 128,256 for something you typed, which is the reading that still says something once the percentage has rounded away to nothing. The denominator is the model's output width rather than the tokenizer's vocabulary, and the two can differ (128,256 against 128,000 here) because a checkpoint pads its embedding for alignment; a rank is a place among the tokens that could have been ranked. The left half keeps reporting the token you are hovering the whole time, so you are always comparing the candidate against the position it would replace.

    Entropy & alternatives

    Confidence answers "how likely was the token it picked?". Entropy answers a different question: "how spread out was the model's whole distribution?". A token can be picked with modest confidence from two close rivals (low entropy, a real coin-flip between two options) or from thousands of vaguely plausible options (high entropy, genuinely unsure). Entropy is reported in nats: 0 means complete certainty, and about 5 nats is roughly an even choice among 150 tokens, which is about as torn as a language model gets.

    Autoregressive runs always capture it. Hovering a token fills the Entropy field in the metrics strip, the Entropy overlay recolors tokens from cool blue (decisive) to hot amber (torn), and an entropy profile appears below the scrubber: one column per position, tall and hot where the model hesitated, with the column for your current frame highlighted. Columns past that frame fade back, so scrubbing to the middle of a run leaves the profile saying the same thing the text above it does about which tokens exist yet. Hovering a token makes its column glow and shows that position's value, in nats, at the right of the profile. Because an autoregressive model decides each position exactly once, that profile reads across the sequence rather than over time.

    Once a run has been edited, every position the edit touched is marked in the profile with a dashed orange line over a faint tint, the same marker the Analytics entropy chart uses and the same color the tokens use for a remask. Unlike the hover glow, it stays put: it names where the run was intervened on, which is true no matter where your cursor is, so you can scrub and crossfade without losing the place the branch was forced.

    The profile and the text cross-highlight, so you can read in either direction: hover a token to light its column, or sweep the profile to light the token behind any column that catches your eye. A token lit this way looks exactly like one under your cursor, since both mean the same thing. Sweeping the profile lights tokens whether or not Highlight tokens is ticked, because following a column back to its word is a way of reading the run rather than a comfort preference.

    After a What If? branch, the profile carries both runs: the pre-edit columns underneath and the branch's on top, mixed by the Original / Edited crossfade below the scrubber. It spans whichever run ran longer, so the columns stay aligned by position even when the branch came out a different length, and the nats readout reports whichever run the crossfade is favoring. Because a branch reproduces its prefix exactly, the two profiles only visibly differ to the right of the substitution, which is itself a reading of how far the intervention reached.

    The Alternatives hyperparameter, on by default, captures the top five candidates at each position as well as the chosen one. Hovering a token then opens a popover listing them with a probability bar each, and the one the model actually chose is highlighted. Whitespace and control tokens are shown with visible stand-ins (· for a space, ↵ for a newline) so an invisible candidate is still legible.

    Sampling does not have to stay inside those five, and at a warm Temperature it often does not. When a position committed a token from outside them, it appears as a sixth row below a dashed rule, carrying its own probability and its true rank, which is frequently in the thousands. It is added rather than swapped in: the five above it are a statement about what the model preferred, and dropping one to make room would quietly make that statement false. The sixth row is not clickable under What If?, since forcing the token already sitting there would regenerate the run to arrive exactly where it started.

    What If? (autoregressive counterfactuals)

    Because a left-to-right model cannot be remasked, it gets a different intervention. After a SmolLM3 run generated with Alternatives on, a What If? button appears beside the scrubber.

    1. Click What If?. Positions that captured candidates pick up a dotted underline.
    2. Hover one to open its candidate popover, then click a candidate to force it.
    3. The model regenerates everything after that position, and you land in the same Confirm / Retry review as a diffusion edit.

    There is no frame-selection step here: for a left-to-right model the frame and the position are the same choice. The continuation is decoded greedily, so what changes downstream is the effect of your intervention rather than fresh sampling noise. Entry auto-saves the original run, and once the branch is confirmed, Diff vs Original becomes available to compare the two.

    Every position you have forced keeps a soft orange wash behind it for as long as the run is on screen, so a long output can be scanned for its interventions instead of remembered. It is a quieter mark than the one a position wears while you are editing it, and it means something different: the bright one says "selected, about to be redrawn", the wash says "this run was intervened on here", which stays true afterwards. Because it sits behind the text rather than coloring it, the Heatmap and Entropy overlays read normally on top of it.

    Typing your own token

    Under the five candidates sits an Enter your own field, for forcing a token the model never weighed. The five are what it considered; this is anything in its vocabulary. Click into the field and a green check and a red cross slide out beneath it; confirm turns your text into a row you click to run, just like a candidate, with a small ↺ beside it if you want to try something else. Escape, the cross, or a click anywhere outside all cancel. While you are typing, the popover stays put and stops following your pointer, so moving to reach the buttons cannot lose what you have written.

    As you type, the field shows what your text actually becomes: the token pieces it resolves to, each with its vocabulary id, in alternating tints so a split inside a word is visible. This is where tokenization stops being an abstraction. unfortunately is likely one token; unfortunatelyy is likely three. You can only confirm at exactly one piece, and the count turns orange when it is not, because a replacement of any other length would shift every position after it and the diff, the entropy profile, and the edit marker all read positionally. The Tokenizer row on the Analytics run detail names the vocabulary these pieces come from.

    The field arrives pre-seeded with a leading space when the token being replaced has one, which is the usual case mid-sentence: most tokenizers carry the space inside the word token, so  cat and cat are different entries and dropping the space would weld your word onto the one before it. That is read from the token you are replacing rather than guessed at, and a single backspace removes it if you want the other one. While the field is empty, or holds only that space, its placeholder spells the space out as a · dot, so a seeded field says so rather than looking untouched.

    A typed token reports its true probability, read from the model's distribution at that position, so the readout can honestly say you forced something the model gave 0.3 percent to. Its entropy is unchanged, because entropy describes how torn the model was at that position, which is a fact about the distribution and not about the token you pushed into it. A candidate you pick from the five keeps the probability its own run recorded.

    Confirming measures that probability straight away, before you commit to running anything, and the solidified row shows it as a percentage beside the retry icon: … for the moment the measurement is in flight, then a figure, floored at <0.1% rather than rounded to a flat zero. It is the same number the run will report afterwards, because the measurement and the substitution read the same distribution. Hover the row to send the full precision to the metrics strip above the output, along with the token's rank among everything the model could have said. Rank is the reading that survives a collapsed percentage: #41,203 of 128,256 tells you how far outside the model's preference you have reached, where <0.1% only tells you that you have.

    Type a token the position already listed and no measurement is taken at all: the row reports the figure the run itself recorded, which is better information than a fresh reading rather than merely a faster one. The model computes in bf16, which carries about three decimal digits, so measuring a position a second time by a slightly different route can land a fraction of a percent away from what the run got the first time. Reusing the run's own arithmetic where it exists sidesteps that, and where the run's attention state is still resident, a genuine measurement reproduces it exactly by making the same call the run made.

    After a branch exists, the candidate popover gains a small ‹ › pager at positions from the substitution onward, flipping between what the Original run and the Edited branch were weighing at the same position. Each page marks the token its own run drew. Positions before the substitution have no pager, because a branch reproduces its prefix exactly, candidates included. Only the Edited page is clickable while What If? is armed: the original run is a record, not something you can substitute into.

    Interactive remasking & resume

    After a generation completes, a frame scrubber appears below the output area for any model. Use the slider or ‹ › buttons to explore frames. Press Left / Right arrow keys or Home / End to navigate. The remasking / resume tools below work for LLaDA and for single-canvas DiffusionGemma runs; they are unavailable for autoregressive runs (SmolLM3, which generates left-to-right) and on multi-canvas DiffusionGemma runs, where Edit Frames is disabled.

    Guided multi-frame editing

    Click the Edit Frames button to enter the guided editing flow:

    1. Select a frame: Navigate to the frame you want to edit and click Select Frame. The scrubber starts at frame 0 and only allows forward navigation.
    2. Remask tokens: Click resolved tokens to remask them (they turn orange). Click again to deselect. When ready, click 🔒 Lock In. For LLaDA the tokens are set back to [MASK]; for DiffusionGemma they are renoised, so committed neighbours may also shift on resume.
    3. Choose next action:
      • Edit Another Frame: enters target selection mode. Navigate to a later frame you want to edit next; a faded preview of the original run is shown at each frame as a reference, with a note that the output will diverge based on your edits. Click Run to Here to resume the model up to that frame. You are then placed directly into edit mode on the target frame.
      • Resume to End: resumes the model from your last edit through all remaining steps to produce the final output.

    A single edit followed by Resume to End is the simplest case; you can also chain as many frame edits as you like. Each partial resume generates only the frames between your last edit and your next target, so earlier edits propagate forward through every subsequent segment. The scrubber enforces forward-only navigation; later edits cannot precede earlier ones.

    Click Exit at any time to leave guided editing; this discards any in-progress edits and restores the original run. All remask edits (frame indices and token positions) are recorded automatically and included in saved results.

    Visual overlays & settings

    A collapsible Overlay drawer in the top-right of the output area recolors the frame you are viewing. While it is collapsed you can drag its handle up and down the right edge to move it off whatever the run has drawn underneath; each page remembers where you left it. Dragged near the bottom, its picker opens upward so the choices stay inside the output area instead of being cut off by its edge. It defaults to None:

    • Heatmap: recolor resolved tokens by confidence (see Confidence & the heatmap above).
    • Entropy: recolor resolved tokens from cool blue (decisive) to hot amber (torn), by how spread the model's distribution was (see Entropy & alternatives above). Listed for runs that carry the signal, which today means autoregressive runs.
    • Commit Order: tint resolved tokens by the step at which they settled, from light green (early) to red-orange (late), with a matching gradient legend in the status bar. Diffusion runs only.
    • Diff vs Original: compare an edited run against the original. Diffusion runs list it up front, disabled until you have edited and resumed a run; autoregressive runs list it once a What If? substitution has produced a branch. When active, a slim row below the scrubber adds independent Original / Edited opacity sliders and a Difference blend toggle (matching tokens cancel to black, divergences glow), plus a Diverged N/total readout.

    Once a run has a branch, an Original / Edited crossfade appears below the scrubber, the same control the Analytics detail modal uses. It stacks the retained pre-edit run under the branch and mixes between them in any overlay, so you can fade the two against each other while reading a Heatmap or an Entropy view rather than only in Diff. Each layer is colored by its own run's values, so at full Original the Heatmap shows the original run's confidence, not the branch's colors under the original text. Whichever side is more opaque takes the pointer, so hovering, the metrics strip, and the candidate popover all read the run you are looking at, the strip names which run that is, and the popover opens on that run's page. The entropy profile below follows the same slider, fading between the two runs' columns. Diff vs Original is the exception and keeps its own two sliders, since a Difference blend needs both layers up at once rather than traded off. The crossfade is hidden while a run is being edited, where the tokens are a target for clicks rather than something to read, and it returns to Edited whenever a run completes.

    Preferences live on a shared Settings page, opened from the gear icon in the header (the Main Menu and Analytics have the same gear). Changes are staged behind Save / Reset, saved on the server, and shared across every page:

    • Render diffusion-style text: dynamic status messages resolve from scrambled block-glyph noise, like a denoising pass; a Mode sub-setting picks Default (resolve once) or Cycle (keep re-diffusing while the status is active). Skipped automatically under reduced-motion.
    • Token birth glow: each token flashes with a soft white glow the instant it is generated, then fades, so a run leaves a visible trail of where the model has just committed. It fires on live generation only, never while scrubbing a finished run, and it is skipped automatically under reduced-motion. Three sub-settings tune it: Tune for picks the model class the other two apply to, then Brightness and Fade time set how strong the flash is and how long it takes to decay. Each class keeps its own pair, because tokens arrive far faster from an autoregressive model than from a diffusion step, and how long a trail you see is roughly the rate multiplied by the fade: what reads well for LLaDA can go by too quickly to notice on SmolLM3, especially on a GPU. Below the sliders, a block of copy doubles as the preview, since there is nothing generating on the Settings page to judge the pair against: its words light up the way that class produces tokens, sweeping left to right for autoregressive and scattering for diffusion. It replays once a drag settles, and clicking it plays again. The order never changes between replays, so two settings can be compared directly rather than against a different shuffle each time. Under reduced-motion it holds a few words lit instead of animating, which still shows brightness even though a fade cannot be shown without movement.
    • Device tag ticker: the scrolling GPU / device readout on the model tag.

    Two preferences do not live there, because each is controlled from the thing it acts on and takes effect immediately rather than needing a Save. Both are still remembered across sessions. Highlight tokens is a checkbox in the Overlay drawer, on this page and in the Analytics detail modal, since it acts on the tokens the drawer sits over; it is on by default, and hovering any token shows its position and confidence for the current frame. The T/s readout in the status bar is the other: clicking it switches between the run average and the last step. Neither is touched by Reset on the Settings page, which would otherwise flip a switch that is not shown there.

    Analytics Suite

    Click Analytics in the header to open the Analytics Suite. It reads saved runs from the results/ directory and provides interactive charts for comparing generation behavior across configurations.

    Run browser

    Runs can be grouped by model, prompt, or any hyperparameter using the Group by dropdown (default: Date, i.e. ungrouped and sorted newest-first). Select a run to view its details, including the model, prompt, hyperparameters, timestamp, processor, and final output. The detail panel also names the tokenizer that produced the run's token ids, on its own row, with its vocabulary size and the model's output width on two more. Those last two are worth reading together: they differ wherever a checkpoint pads its embedding for alignment (128,256 against 128,000 for SmolLM3), and the wider one is the denominator a candidate's rank is quoted against, while the narrower one sets the entropy ceiling of ln(vocabulary). All three are recorded per run from the loaded model rather than looked up per model name, so they stay correct for an old run whose checkpoint has since changed. Runs saved before a figure was recorded omit its row. The table shows columns shared across models; model-specific hyperparameters stay in the detail panel. To remove a run, click its trashcan action: a confirmation modal shows the run's folder path (results/<timestamp>_<model>) and a toast confirms the deletion.

    Token overlay

    The detail modal centers a token view of the run with its own Overlay drawer (top-right) and a frame scrubber that replays every saved frame, mirroring the generator (it opens on the final frame). The overlays are None, Heatmap (recolor resolved tokens by persisted confidence), Entropy (for runs saved with the signal), Commit Order (tint by the step each token settled on), and Diff vs Original (for edited runs saved with their pre-edit snapshot: stacks the original and edited runs with independent Original / Edited opacity sliders, a Difference blend toggle, and a Diverged N/total readout). Commit Order applies to diffusion runs only; Diff appears for any edited run, including an autoregressive What If? branch. Runs saved with captured candidates also get the generator's hover popover, so a decision and the branch taken from it stay inspectable long after the run. Runs saved before durable overlays (or without token data) show a short unavailable note.

    For an edited run saved with its pre-edit snapshot, an Original / Edited crossfade sits at the right of the Token overlay heading row, above the text it blends. It governs the token view, which stacks both runs and blends between them in any overlay, and the entropy chart's bars follow the same slider. The timing and confidence charts follow it too, but only while it is being dragged, because those two have their own pins (see Comparing two runs on the line charts). Each layer is colored by its own run's values, so at full Original the Heatmap shows the original run's confidence rather than the branch's colors under the original text. Whichever side is more opaque takes the pointer, so hovering, the candidate popover, and cross-highlighting always read the run you are looking at. Diff vs Original is the exception: it keeps its own two sliders, because the Difference blend needs both layers up at once.

    Convergence chart

    Plots the percentage of resolved (unmasked) tokens at each frame. The curve shows how quickly the model commits to its output. If the run includes user remask edits, the transition segments leading into edited frames are highlighted in blue, and hovering reveals which token positions were remasked.

    Timing charts

    One slot holds two charts; the small arrows beside the heading flip between them. Elapsed Time plots cumulative elapsed time per frame. Time accumulates across resume operations so the chart shows total wall-clock cost. Transition segments into remasked frames are highlighted in green, and the resumed stretch after an edit is drawn in a lighter blue. The processor that produced the run is listed in the run summary above the charts.

    Tokens per Second plots the same run as a rate: how many tokens it had produced by each frame, over how long it had taken to get there. It is a running average rather than a per-step reading, which on a diffusion run would mostly trace the sampler's reveal schedule. Nothing extra is stored for it, so it works on runs saved long before the metric existed. The pre-edit comparison is offered for autoregressive runs only: a saved run keeps the original's frame timings but not its canvas, and a rate needs both.

    The run summary reports elapsed time beside these. An unedited run gets one figure; an edited run gets two, Elapsed (original) for the run it branched from and Elapsed (edited) for the prefix it inherited plus everything generated after, so you can see whether the intervention cost time.

    Confidence chart

    Plots the mean per-token confidence at each frame, which typically climbs toward 100% as a canvas converges. This makes DiffusionGemma's adaptive stopping visible: confidence rises and then a canvas commits. Shown only for runs saved with confidence data.

    Comparing two runs on the line charts

    An edited run saved with its pre-edit snapshot draws both runs on the timing and confidence charts at once: the original solid in grey, the branch dashed in the chart's own color. Both share a prefix and separate at the edit, so the point where the dashes leave the solid line is the cost or the confidence the intervention actually changed. The gap between them is washed in, which turns that cost into an area you can see the size of rather than a distance you have to measure by eye. It is colored by whichever run is on top of the gap: the branch's own color where the branch is higher, grey where the original is. That way the band never claims one direction is the good one, which matters because higher means slower on the timing chart but better on confidence. Since the two runs share their prefix exactly, the band starts empty and opens up only where the intervention reached.

    Two pins in each chart header choose which runs are drawn, 1 for the original and 2 for the branch, lit green when that run is showing. Both are on when a run opens. One of the three states (original, branch, or both) always holds, so the last lit pin cannot be turned off: a chart drawing neither run has nothing in it to read. Unpinning either run also takes the band with it, since a gap needs both of its edges to mean anything.

    Dragging the Original / Edited crossfade above the token view borrows these two charts for the length of the drag, so the whole modal moves together, and they ease back to their pins the moment it is released. The pins dim while that is happening. The crossfade is the token view's control, not theirs, so the borrow is deliberately momentary; adjusting the slider with the arrow keys moves the tokens and the entropy bars only.

    Entropy chart

    The one chart indexed by token position rather than by frame, which is why it is drawn as bars: an autoregressive model decides each position exactly once, so its entropy is a property of the position, not a point in a time series. One bar per generated token, colored on the same cool-blue to hot-amber ramp as the Entropy overlay, so tall warm bars mark the moments the model was torn. Hovering lights the column and names the token at that position alongside its value in nats, the same highlight the generator's entropy profile uses, and it also lights the matching token in the overlay above and fills the metrics strip there. That works in reverse too: hovering a token lights its bar. Scrubbing the token view fades the bars past the current frame, so the chart and the text agree on which tokens exist at the frame you are looking at. Shown for runs saved with the entropy signal, which today means autoregressive runs.

    If the run carries edits, a dashed orange marker and a faint tint of the same color sit on each edited position, matching the color the generator uses for remasks and substitutions. From that position rightward the tooltip splits into two rows, Original and Edited, since that is where a What If? branch stops sharing its prefix and the two runs become worth comparing. At the marked position itself both rows show the same nats and different tokens: entropy describes the distribution the prefix produced, and forcing a token changes which one was drawn, not the distribution it was drawn from.

    For edited runs saved with their pre-edit snapshot, the Original / Edited crossfade above the token view blends this chart's two bar layers along with the text. Left shows the original run's bars at full opacity, right the branch's, and anywhere between blends the two. Because the branch copies its prefix verbatim, the crossfade only visibly moves to the right of the marker, which is itself a reading of how far the intervention reached.

    Canvas boundaries

    For multi-canvas DiffusionGemma runs, dashed amber markers on the convergence, timing, and confidence charts mark the frames where one canvas commits and the next begins. Single-canvas runs (including all LLaDA runs) show no markers.

    Chart controls

    Every chart supports scroll-wheel zoom and a + / − / Reset cluster docked in the chart's bottom-left corner, which brightens on hover. Tooltip boxes park in whichever corner of the plot area is free of both the data and the pointer, preferring top-left and falling back through top-right, bottom-left, and bottom-right, and they stay fully inside the plot area rather than spilling onto the axes. Each chart has an eye toggle to hide/show its box. When every corner is occupied and the box has nowhere clear to go, the covered segment and the hovered point glow through it.

    Saving results

    The Save button (the down-arrow icon to the left of Generate) becomes enabled once a run completes. Clicking it saves the run to a timestamped folder under results/ containing:

    • metadata.json: prompt, hyperparameters, final output text, reproducibility info (seed, GPU, git commit, library versions, and the tokenizer that produced the run's ids), and any remask edits.
    • final.txt: the decoded final text.
    • history.txt: frame-by-frame snapshots of the diffusion process.
    • tokens.json: per-frame token records (text, mask flag, vocab id, confidence, and entropy where captured) that drive the durable overlays in Analytics.
    • alternatives.json: the captured top-five candidates per position, written only for runs generated with Alternatives on.
    • diffusion.gif: an animated GIF visualizing the denoising progression.

    It is disabled during generation and after a successful save (to prevent duplicates); while saving it shows a spinner, then a brief checkmark. Starting a new generation resets it.

    Experimental mode

    The toggle above the parameter controls removes the recommended bounds, allowing extreme values for exploratory purposes. The default bounds represent the range that produces more consistent, stable results.

    Hyperparameters between visits

    Your hyperparameters, the Experimental toggle, and whatever is in the prompt box are kept for as long as the app is open, so a trip to Analytics and back leaves your setup exactly as you left it. Each model remembers its own values, and a half-typed number is preserved as typed rather than rounded off. Closing the app clears all of it: a fresh launch starts from the recommended defaults, which is the state worth starting from.

    Reset, at the right of the Experimental row, puts every hyperparameter and the Experimental toggle back to their defaults for the current model and device. It is greyed out whenever nothing has been changed, so it doubles as a readout of whether you are on defaults. Your prompt is left alone, and the button is unavailable while a generation is running.
